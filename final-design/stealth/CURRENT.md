## 3. Who may mint, burn, move
- RD mint: only `issuer` (`mint` RupiahDigital.sol:33-36, `mintStealth` :38-48, both `if (msg.sender != issuer) revert OnlyIssuer()`). Burn: any holder `burn(uint256)`, and `burnFrom` by allowance (ERC20Burnable). Transfer: `transfer` and `sendStealth` (announces in the same tx, RupiahDigital.sol:52-84).
- DFABI issue: `issueByPartitionStealth` and `issue*` are `onlyMinter isIssuableToken` (DfabiBond.sol:44); the deployer is a minter. Because `isControllable` is true and the deployer is the only controller, BI can force-move any holder's DFABI (ERC-1400 controller transfer, vendor/universal-token; read from code, not executed). Every `transferByPartitionStealth` needs a certificate signed by BI (docs/architecture-brief.md:456-461; ts/chain.ts:47-49).
- Units: RD decimals 0 (1 unit = 1 rupiah, matches `PRICE_PER_UNIT = 1_000_000n`, frontend/server/src/domain.ts:14); DFABI `decimals() 18` but `granularity 1` and Lensa uses whole units; wallets that honour `decimals()` would show a DFABI unit as 1e-18 while RD shows whole units.
- DvP: `DvPFactory.create` (custodian only) deploys a `DvPEscrow` per trade; `settle` only before `expiry`, `cancel` by anyone from `expiry` on; refunds go to the original owners (DvPEscrow.sol:103-142). A failed run leaves a record in the state `escrowed` list (rd-lensa-frontend #11).
